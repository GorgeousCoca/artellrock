# Архитектура сайта «Баня к даче» (bany-k-dache.pro)

Основа: статья AWG «Архитектура сайта: основы проектирования для стабильной работы и роста» (09.04.2026) + разбор текущего сайта https://bany-k-dache.pro/.

## 1. Что есть сейчас (аудит)

Сайт — одностраничный лендинг-визитка производителя каркасных бань (Пестово): серии БКС (от 530 000 ₽) и БКМ (от 800 000 ₽), оплата после установки, доставка до 500 км, FAQ, видеообзоры (VK), видеоотзывы, форма «три контакта», телефон и VK.

| Проблема | Почему важно (по статье) | Решение |
|---|---|---|
| Нет `sitemap.xml` и `robots.txt` (оба отдают 404) | Роботы по структуре определяют главные страницы и быстрее индексируют новые | Генерировать автоматически (раздел 6) |
| Весь контент на одной странице | Нет иерархии: один URL не ранжируется по запросам «баня БКС», «каркасная баня 6 м», «баня с доставкой в <регион>» | Иерархическая структура с отдельными URL (раздел 3) |
| Ссылки «Смотреть проекты», «Как проходит заказ», «Базовая комплектация», «Дополнительные возможности» — это якоря/модалки без самостоятельных страниц | Нет внутренней перелинковки и точек входа из поиска | Сделать полноценные страницы |
| Видео и отзывы встроены с VK | Тяжёлые сторонние скрипты бьют по LCP/INP | Фасад (постер + загрузка по клику) |
| Нет структурированных данных | Нет расширенных сниппетов (цена, FAQ, отзывы) | Schema.org (раздел 6) |

## 2. Принципы (из статьи → применение)

- **Две архитектуры:** информационная (структура, навигация, перелинковка, URL) и техническая (frontend, backend, БД, API) проектируются отдельно, но согласованно.
- **Модульность и разделение ответственности:** frontend только отображает; бизнес-логика (приём заявок, валидация, интеграции) — на сервере.
- **Адекватность масштабу:** в статье микросервисы нужны при каталоге в 100 тыс. SKU. Здесь 2 серии и десятки проектов, поэтому **модульный монолит**, а не микросервисы. Границы модулей оставляем чёткими, чтобы при росте выносить их отдельно.
- **Нефункциональные требования** (фиксируем до выбора стека):
  - TTFB ≤ 300 мс, LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на мобильных (основной трафик — дачники с телефонов, часто на слабом 4G);
  - доступность ≥ 99,9%;
  - потеря заявки недопустима (заявка — главная конверсия);
  - соответствие 152-ФЗ (персональные данные: имя, телефон).

## 3. Информационная архитектура

### 3.1 Тип структуры
Иерархическая (дерево) для каталога и контента. Линейная (воронка) — только для пути «подбор → заявка → договор».

### 3.2 Карта сайта

```
/                                  Главная (лендинг: оффер, серии, доверие, FAQ, форма)
├── /bani/                         Каталог бань (хаб)
│   ├── /bani/bks/                 Серия БКС (5–8 м × 2,4 м, от 530 000 ₽)
│   │   └── /bani/bks/bks-7-5x2-4/ Карточка проекта
│   └── /bani/bkm/                 Серия БКМ (8–12 м × 4,6 м, от 800 000 ₽)
│       └── /bani/bkm/bkm-6/       Карточка проекта (напр. БКМ-6, 9 × 4,6 м)
├── /komplektaciya/                Базовая комплектация
│   └── /komplektaciya/dopolnitelno/  Дополнительные возможности и опции
├── /kak-zakazat/                  Как проходит заказ (линейный сценарий: заявка → расчёт → договор → производство → установка → оплата)
├── /dostavka-i-ustanovka/         Доставка до 500 км, установка за 1 день, схема винтовых свай
├── /otzyvy/                       Видеоотзывы и отзывы с Авито
├── /video/                        Видеообзоры
├── /proizvodstvo/                 Производство, реальные фото, сроки (от 20 дней)
├── /faq/                          Частые вопросы (расширенный)
├── /blog/                         Статьи (фундамент, свайный фундамент, уход за баней…)
│   └── /blog/<slug>/
├── /kontakty/                     Телефон, VK, адрес производства (Пестово)
├── /politika-konfidencialnosti/
├── /politika-cookie/
└── /raschet/                      Страница заявки (отдельный URL для рекламы и мессенджеров)
```

Правила URL (из статьи): латиница, короткие, читаемые, без ID и параметров, trailing slash единообразно, одна каноническая версия. Параметры UTM не индексируются (`rel=canonical`).

### 3.3 Навигация
- **Главное меню (максимум 6 пунктов):** Бани · Комплектация · Как заказать · Доставка · Отзывы · Контакты.
- **Закреплённый CTA:** «Узнать стоимость» + телефон +7 909 566-60-90 + VK. На мобильных — нижняя панель (позвонить / написать / рассчитать).
- **Хлебные крошки** на всех страницах глубже первого уровня (+ `BreadcrumbList`).
- **Правило 2–3 кликов:** с любой страницы до заявки — 1 клик, до карточки конкретной бани — не более 3.
- **Футер:** все разделы, политики, контакты, ссылка на VK.

### 3.4 Внутренняя перелинковка
- Карточка проекта → её серия → каталог (вверх по иерархии).
- Карточка → «Похожие проекты» (соседние длины в серии, другая серия) — аналог «С этим товаром покупают».
- Карточка → «Что входит в комплектацию», «Как проходит заказ», «Доставка», видеообзор этого проекта.
- FAQ-ответы → соответствующие страницы (фундамент → блог про сваи, комплектация → /komplektaciya/).
- Статьи блога → 1–2 карточки проектов и страница заявки.

## 4. Техническая архитектура

### 4.1 Общая схема

```
Браузер (Next.js App Router, SSG/ISR, SCSS)
   │
   ▼
CDN / reverse proxy (Caddy или Nginx): TLS, HTTP/2-3, brotli, кэш статики
   │
   ├── Next.js (Node) ── страницы: статическая генерация + ISR
   │       │
   │       ├── Route Handlers /api/lead  ──► Lead-модуль ──► БД (заявки) ──► уведомления (Telegram/e-mail/CRM)
   │       └── Revalidate-webhook ◄── CMS (при публикации контента)
   │
   ├── Headless CMS (Payload CMS) ── админка для владельца: проекты, комплектация, FAQ, отзывы, блог, настройки
   │       └── PostgreSQL (контент + заявки)
   │
   └── Object storage (S3-совместимое) ── фото/видео производства, обработка в AVIF/WebP
```

### 4.2 Frontend
- **Next.js (App Router) + TypeScript + SCSS Modules.** Страницы каталога, комплектации, FAQ, блога — статические (SSG) с ISR; форма — клиентский компонент.
- Server Components по умолчанию, клиентский JS — только для формы, галереи, меню.
- Изображения: `next/image`, AVIF/WebP, `srcset`, явные размеры (CLS = 0), `priority` только для hero.
- Видео VK/YouTube — **фасад**: постер + кнопка, iframe подгружается по клику.
- Шрифты: self-hosted, `font-display: swap`, subset кириллицы.
- Доступность: семантическая вёрстка, фокус, контраст, `aria` для аккордеона FAQ и галереи.

### 4.3 Backend (модульный монолит)
Границы модулей — как будущие границы сервисов:

| Модуль | Ответственность |
|---|---|
| `catalog` | Серии, проекты, комплектация, опции, цены «от» |
| `content` | FAQ, блог, отзывы, видео, страницы |
| `leads` | Приём заявки: валидация, антиспам, сохранение, уведомления |
| `integrations` | Telegram-бот, e-mail, CRM (amoCRM/Bitrix24), Яндекс Метрика (цели) |
| `seo` | sitemap, robots, canonical, JSON-LD, редиректы |
| `admin` | Роли и права, аудит изменений |

### 4.4 Данные
- **PostgreSQL** — единая реляционная БД: контент, проекты, заявки. Заявки требуют ACID (потеря недопустима).
- **Redis** — по необходимости (rate limit формы, кэш). На старте можно не вводить.
- Модель (сущности): `Series` 1—N `Project`; `Project` N—N `Option`; `Project` 1—N `Media`; `Testimonial` → `Project?`; `FaqItem`; `Post`; `Lead` (имя, телефон, регион доставки, интересующий проект, UTM, согласие, статус, время).
- Бэкапы БД ежедневно + хранилище медиа с версионированием.

### 4.5 API
- Публичный: `POST /api/lead` (единственная запись), чтение контента — только на этапе сборки/ISR.
- Контракт: JSON, валидация (Zod), коды ошибок, идемпотентность (ключ заявки против дублей).
- Админ-API — внутри CMS, закрыт аутентификацией.

### 4.6 Критический поток: заявка
1. Пользователь вводит имя, телефон, регион доставки + согласие на обработку ПДн.
2. Клиентская валидация → `POST /api/lead` (honeypot + rate limit + при необходимости Yandex SmartCaptcha).
3. Сервер валидирует, **сначала пишет в БД**, потом асинхронно шлёт уведомления (Telegram → менеджер, e-mail, CRM). Сбой уведомления не теряет заявку; есть повторные попытки.
4. Ответ клиенту + отправка цели в Метрику.
5. Резервный путь при сбое: кнопки «позвонить» и «написать во ВКонтакте» всегда на странице.

### 4.7 Инфраструктура и надёжность
- Хостинг в РФ (Selectel / Timeweb / VK Cloud) — ПДн граждан РФ хранятся на территории РФ (152-ФЗ).
- Docker Compose: `web` (Next.js), `cms`, `postgres`, `caddy`. CI/CD: сборка → тесты → деплой; откат на предыдущий образ.
- Мониторинг: аптайм-проверки главной и `/api/health`, алерты в Telegram, логи ошибок (Sentry/GlitchTip).
- Нагрузочное тестирование перед кампанией контекстной рекламы (k6): проверка страницы и формы.
- Безопасность: HTTPS + HSTS, CSP, ограничение размера тел запросов, секреты в окружении, 2FA в админке, обновления зависимостей.

## 5. Сквозное: производительность и аналитика
- Бюджет: JS ≤ 150 КБ на страницу, изображения hero ≤ 150 КБ, нет блокирующих сторонних скриптов.
- Яндекс Метрика (вебвизор, цели: просмотр цены, клик по телефону, клик VK, отправка заявки) + корректный cookie-баннер (до согласия аналитика не грузится).
- Замер Core Web Vitals по реальным пользователям, проверка по Lighthouse CI в пайплайне.

## 6. SEO-слой
- Автогенерация `sitemap.xml` и `robots.txt` (с указанием Sitemap, закрыты `/api`, `/admin`).
- JSON-LD: `Organization`/`LocalBusiness` (Пестово, телефон), `Product` + `Offer` (цена «от») для карточек, `FAQPage`, `BreadcrumbList`, `VideoObject`, `Review`.
- Уникальные `title`/`description`/H1 на каждый URL; Open Graph для шаринга в VK/Telegram.
- Семантика: отдельные страницы под кластеры запросов — «каркасные бани под ключ», «баня БКС», «баня БКМ», «баня с доставкой», «баня без предоплаты» + региональные посадочные (по необходимости).
- Редиректы со старых якорных URL, единая каноническая версия домена.

## 7. Этапы внедрения

1. **Информационная архитектура:** семантическое ядро (Яндекс Вордстат), анализ конкурентов, утверждение карты сайта.
2. **Требования:** NFR (раздел 2), список интеграций (Telegram, CRM, Метрика).
3. **Каркас:** Next.js + Payload CMS + PostgreSQL, модели данных, дизайн-система, `/api/lead`.
4. **Контент:** перенос текущего лендинга, карточки проектов, комплектация, FAQ, отзывы.
5. **SEO + аналитика:** sitemap, robots, JSON-LD, цели Метрики, редиректы.
6. **Нагрузочное тестирование, аудит CWV, запуск, мониторинг.**
7. **Развитие:** блог, региональные страницы, калькулятор стоимости, CRM-воронка.

## 8. Когда пересматривать архитектуру

Переходить к headless с отдельными сервисами и балансировщиком имеет смысл, если: каталог вырастет до сотен позиций с онлайн-конфигуратором и оплатой, появятся личный кабинет клиента или интеграция с производством, либо одна из функций начнёт упираться в нагрузку. До этого модульный монолит дешевле в поддержке и быстрее в доработках.
